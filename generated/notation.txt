3) Separate Notation for Boolean Values (Bool : Type)
--------------------------------------------------------------------------------
Question: "Also do we need a separate notation for boolean values or not?"
Answer:   YES — a separate notation for boolean values (b : Bool) is strictly
          necessary to eliminate ambiguity between three distinct layers:
            (i)   Syntactic formulas of the object theory (T / F, ⊤ / ⊥, \top / \bot : Fm)
                  in Variant 1, which are syntactic AST objects proved by sequents;
            (ii)  Constructive types (Unit / Void, 𝟙 / 𝟘, \mathbf{1} / \mathbf{0} : Type)
                  in Variant 2, which are inhabited by proof/program terms; and
            (iii) Boolean data values (true / false : Bool), which are the two
                  canonical term inhabitants of the two-element computation type
                  Bool (UBool in typetheory.ML), passed as arguments to polymorphic
                  conditionals simple_if(T_e, b, t_1, t_2), dependent conditionals
                  if_dep(T_e, b, t_1, t_2) with T_e : Bool -> Type (selecting
                  branch types T_e(true) and T_e(false)), and decidable SML/kernel
                  boolean side-conditions (isFree, FFI, NFV, Ctx_eq).

5.2 Context Environments: Δ (Signature/Sorts) vs Γ (Proof Hypotheses)
--------------------------------------------------------------------------------
In judgements Δ; Γ ⊢ e : T:
  • Context Δ (Signature / Variable Sort Environment):
    Tracks declared object-level class/type variable identifiers and their sorts.
    Example: Δ = { z : Class, A : Type, F : Class }.
    Variables in Δ are introduced by universal / parametric binders:
      ELam: (Δ, z : Class; Γ ⊢ e : T) ==> (Δ; Γ ⊢ Lam (z:Class) => e : ∀(z:Class), T).

  • Context Γ (Proof Hypothesis Environment):
    Tracks active antecedent propositions / hypotheses available for logical deduction.
    Example: Γ = { hIn : z ∈ {x | ⊥}, hSub : A ⊆ B }.
    Hypotheses in Γ are introduced by implication binders:
      EFn:  (Δ; Γ, h : P ⊢ e : Q) ==> (Δ; Γ ⊢ fn (h:P) => e : P → Q).


5.3 Glossary of Specific Class-Theoretic Structures
--------------------------------------------------------------------------------
1. Dunaev Pair (Dunaev Tagged Ordered Pair):
   • Notation:   (A, B)_D  ≡  mark(A, 1) ∪ mark(B, 2)  =  ({1} × A) ∪ ({2} × B)
   • Definition: In Morse-Kelley class theory, proper classes cannot be elements
     of sets or classes. Standard Kuratowski pairing ⟨a, b⟩_K = {{a}, {{a, b}}} fails
     when either a or b is a proper class (such as V or On), because {{V}} requires
     V ∈ {V}, which is false in MK. Dunaev tagged ordered pairing solves this by
     disjoint union tagging.
   • Properties: Satisfies projection axioms π₁((A, B)_D) = A and π₂((A, B)_D) = B,
     and pair injectivity (A, B)_D = (C, D)_D <==> (A = C ∧ B = D) for arbitrary
     classes (both sets and proper classes).
   • Source:     Georgy Dunaev, "Morse-Kelley Class Theory with Tagged Ordered Pairs
                 and Tarski-Grothendieck Universes", program/types/foundations.ML,
                 entries 3.76 (DefDunaevOrderedPair), 3.77 (ThmDunaevFirstProjection),
                 and 3.78 (ThmDunaevSecondProjection).

2. Dunaev Class-List:
   • Notation:   [] (empty list), [X₁, ..., X_n] (finite sequence of classes).
   • Definition: Inductively generated sequence of classes defined via iterated
     Dunaev tagged pairing: [X] = (X, [])_D, [X₁, X₂] = (X₁, (X₂, [])_D)_D.
   • Purpose:    Enables class-level multi-argument function domains, explicit
     substitution environments, and sequent hypothesis contexts without ascending
     to conglomerates.
   • Source:     program/types/foundations.ML (entry 3.39: DefClassLists).
